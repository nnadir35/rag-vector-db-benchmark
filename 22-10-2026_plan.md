RAG Vector DB Benchmark — thesis-grade metrics upgrade

Context

The existing scripts/benchmark_db.py (1549 lines) is the core of a thesis benchmark comparing
6 vector DBs (Chroma, Qdrant, FAISS, Milvus, ElasticSearch, Weaviate). It already produces
official scale-experiment JSONs under experiments/results/ (S1–S6) that must not be
regenerated or edited. The user needs the measurement methodology hardened for thesis-quality
rigor: percentile latencies (p99), real QPS, indexing throughput, an explicit MRR@k, per-query
result capture (for proper bootstrap CIs instead of treating 3 deterministic repeats as
independent samples), an exact-vs-ANN recall experiment, ANN parameter sweep infrastructure,
container-level (not process-level) resource measurement for Dockerized DBs, more reliable
disk-size measurement, full reproducibility metadata, and validation of a specific suspicious
result file (S3 Chroma disk size). All changes must be additive JSON fields, must not modify
experiments/results/*.json officials, must not change existing CLI defaults/behavior, and must
not auto-launch large benchmark runs.

Everything below reuses existing helpers instead of duplicating: run_with_resource_stats,
_find_container_name/_DOCKER_DB_PATHS/measure_disk_size_mb, _evaluate_with_repeats,
RetrievalEvaluator/metrics.py, _select_queries_for_documents, _print_table.

Add mrr_at_k(retrieved_ids, relevant_ids, k) -> float: same as mrr() but returns 0.0 if the

3b. New DockerStatsSampler + extend run_with_resource_stats

New class mirroring ResourceSampler but polling
docker stats --no-stream --format "{{.MemUsage}}\t{{.CPUPerc}}" <container> in a background
thread (interval ≥0.2s, since --no-stream itself takes ~100-300ms). Parses "123.4MiB / 2GiB"

(new optional kwarg, default None = fully unchanged behavior/return shape (result, ResourceStats)).

for backward compat with existing consumers) and a DockerStatsSampler concurrently; merge the
docker figures into the returned ResourceStats's new container_* fields and set
resource_measurement_scope="container".

3d. _evaluate_with_repeats — restructure into (time) → (score) phases; p99, real wall-clock QPS, warm-up count, always-on query-level rows

Structural change: split each repeat into two passes instead of interleaving retrieval and
evaluator.evaluate() in one loop. Pass 1 times only the retrieve_fn calls end-to-end with a
single perf_counter() bracket around the whole pass (after warm-up, before any metric
computation); pass 2 (untimed) computes metrics from the stored results. This is required for a
correct wall-clock QPS and is a prerequisite for correct combined embed+search percentiles (see
below) — evaluator overhead must not leak into either.

t_wall0 = time.perf_counter()
timed: list[tuple[Query, RetrievalResult, float]] = []
for q in tqdm(bench_queries, ...):
t_r0 = time.perf_counter()
result = retrieve_fn(query_embeddings[q.id], top_k, q.id)
lat_ms = (time.perf_counter() - t_r0) * 1000.0
timed.append((q, result, lat_ms))
wall_elapsed_s = time.perf_counter() - t_wall0        # real bracketed wall-clock, search-only
latencies_ms = [lat for _, _, lat in timed]

--- untimed scoring pass ---

rows = []
for q, result, lat_ms in timed:
gt = set(ground_truth.get(q.id, set()))
m = evaluator.evaluate(result, gt)
rows.append(m)
...(query_level_results / per_query_details accumulation, repeat_idx == 0 only)...

Add warmup_query_count: int = WARMUP_COUNT param (replaces the hardcoded module constant at
the call site only; default preserves current behavior exactly).

Add container_name: str | None = None param (→ run_with_resource_stats).

Add query_embedding_latencies_ms: dict[str, float] | None = None param — per-query embedding
time captured once, shared across all DBs (see 3e). When provided, build a combined per-query
total latency = lat_ms + query_embedding_latencies_ms[q.id] for every query in timed,
collect into combined_latencies_ms per repeat, and compute total_latency_p50/p95/p99_ms from
that real combined distribution (never search_percentile + avg_embedding_time — the user
flagged that pattern as statistically wrong; it is not applied to any new field). Aggregate
mean/std across repeats same as search-only percentiles.

Add per_repeat_p99_ms via _percentile(latencies_ms, 99) (search-only); aggregate
p99_ms_mean/p99_ms_std alongside existing p50/p95 aggregation.

QPS — two clearly-named, separately reported figures per repeat (never conflated):

wall_clock_search_only_qps = len(bench_queries) / wall_elapsed_s — the primary metric
per the spec, based on the real bracketed wall-clock of the timed pass.

service_time_sum_qps = len(bench_queries) / (sum(latencies_ms) / 1000.0) — a secondary
sum-of-service-times–based estimate, named explicitly as such so it's never mistaken for a
wall-clock measurement.

Embedding-inclusive variants of both, using query_embedding_total_ms (shared, already
measured once): wall_clock_qps_incl_query_embedding and
service_time_sum_qps_incl_query_embedding.

All four aggregated to _mean/_std across repeats.

Always (no longer gated behind dump_per_query) accumulate, for repeat_idx == 0 only, a
compact query_level_results: list[{"query_id", f"recall@{top_k}", "rr", f"ndcg@{top_k}"}] —
pulled straight from the evaluator.evaluate(result, gt) dict already computed in the scoring
pass (tag with query_id; "rr" = that query's mrr@{top_k} value via the new mrr_at_k).
Cheap (metrics already computed), and is the raw material for the bootstrap CI scripts (item 5).
Existing per_query_details (raw retrieved-chunk dump, gated behind dump_per_query) untouched.

Return dict gets new keys: p99_ms_mean/std, wall_clock_search_only_qps_mean/std,
service_time_sum_qps_mean/std, wall_clock_qps_incl_query_embedding_mean/std,
service_time_sum_qps_incl_query_embedding_mean/std,
total_latency_p50/p95/p99_ms_mean/std (only when query_embedding_latencies_ms given),
query_level_results (always present).

New standalone scripts (6 files, all additive, never touch official results)

4a. scripts/exact_knn.py (shared helper module) — memory-safe, genuinely exact

def exact_topk_per_query(query_embeddings, corpus_embeddings, chunk_ids, k, batch_size=2048) -> dict[str, list[str]]. Correctness/memory requirements (200K+ corpus must not OOM):

Never materialize the full query×corpus similarity matrix at once.

Prefer faiss.IndexFlatIP (embeddings assumed normalized elsewhere in the pipeline → inner
product = cosine) built directly via the raw faiss API — not FAISSRetriever/
FAISSRetrieverConfig, to avoid any accidental dependency on a config default that could select
index_type="hnsw". IndexFlatIP/IndexFlatL2 are exact brute-force by construction (no
approximation, no graph/quantization) — assert/log the index class name so the "exact, not
approximate" property is verifiable in the output metadata ("exact_method": "faiss.IndexFlatIP").
Add corpus vectors and query in batches (index.search(query_batch, k)), never a single dense
(num_queries, num_corpus) array.

If faiss is not importable, fall back to batched NumPy: iterate the corpus in
batch_size-row blocks, compute query_batch @ corpus_block.T per block only (bounded memory),
maintain a running top-k per query across blocks via np.argpartition, merge at the end.
Record "exact_method": "numpy_batched" in that case.
Used by both 4b and 4c so the sweep script doesn't duplicate the exact-kNN logic.

4b. scripts/exact_vs_ann_benchmark.py (item 6)

Imports load_dataset_corpus, FixedSizeChunker, SentenceTransformersEmbedder from
scripts/benchmark_db.py to reuse the exact same corpus/embedding/query-selection pipeline, plus
the 5 official-benchmark retriever classes/configs (Chroma, Qdrant, Milvus, ElasticSearch,
Weaviate). FAISS is used here only as the exact-kNN baseline helper (via exact_knn.py's raw
faiss.IndexFlatIP), never as a 6th "official benchmark DB" — the script's own output metadata
explicitly labels it "faiss_role": "exact_baseline_helper" and separately records
"official_benchmark_dbs": ["chroma", "qdrant", "milvus", "elasticsearch", "weaviate"] (5, per
Official Scale Experiment A), adding FAISS to that list only if the run was invoked with
--include-faiss mirroring benchmark_db.py's own existing flag — so no run of this script ever
fabricates a "6 DB official benchmark" label unless FAISS genuinely ran as a benchmarked DB too.
For the same fixed query set + same chunk embeddings: compute exact top-k via
exact_knn.exact_topk_per_query, then for each of the 5 (or 6, if --include-faiss) DBs, get its
ANN top-k (retrieve_with_embedding), and compute
ann_recall_vs_exact@k = |ann_topk ∩ exact_topk| / k per query, averaged per DB. Written to
experiments/results/exact_vs_ann_<num_docs>docs_<ts>.json — new filename pattern, fully separate
from official_scale_* / qrels-based mean_recall_* / gold recall@k. Never modifies or
regenerates any existing official file.

4c. scripts/ann_param_sweep.py (item 7)

CLI: --db {qdrant,milvus,elasticsearch,weaviate,chroma}, --param {hnsw_ef_search,num_candidates},
--values 32,64,128,256, plus the standard num-documents/num-queries/top-k/config flags (reusing
argparse patterns from benchmark_db.py). For each value: dataclasses.replace(cfg, **{param: value}), index once, call evaluate_with_repeats (imported), and (optionally, if --with-exact
given) compute ann_recall_vs_exact@10 via exact_knn (same memory-safe helper as 4b — safe at
200K+ scale). Records one row per value: {param_value, "recall@10", "ann_recall_vs_exact@10", p50/p95/p99, wall_clock_search_only_qps}. Writes both JSON and CSV to
experiments/results/ann_sweep<db><param><ts>.{json,csv} — a plain table for a recall-latency
Pareto plot; no combined/weighted score is computed, per spec.

4d. scripts/query_level_bootstrap_ci.py (item 5, analysis-only, single-DB)

Reads query_level_results_{db} from a given result JSON (--input path.json --db chroma).
Core function bootstrap_ci(values: list[float], n_samples=10000, seed=42, alpha=0.05) -> (mean, lo, hi) — percentile bootstrap over the query axis (resampling which queries, not the
3 deterministic repeats — per the requirement, the repeats are never treated as independent draws
for this CI). Pure numpy (no new dependency). Reports 95% CI for recall@k, rr/MRR@k, ndcg@k
per DB, printed + optionally written to a report JSON.

4e. scripts/paired_bootstrap_delta.py (item 5, DB-vs-DB significance)

--input path.json --db-a chroma --db-b qdrant --metric recall@10. Loads
query_level_results_{db} for both DBs, inner-joins on query_id (asserts the two DBs were
evaluated on the identical query set — true by construction since both come from the same
bench_queries/query_ids_used), computes the per-query paired difference
metric_a[q] - metric_b[q], then bootstraps that paired-difference vector (resampling query
pairs jointly, preserving the pairing) to a 95% CI on the mean delta. Reports whether the CI
excludes 0 (i.e., a significant difference at the 95% level) without computing any single
combined "winner" score. Reuses bootstrap_ci from 4d.

4f. scripts/validate_s3_chroma_disk.py (item 12)

Read-only: loads official_scale_experiment_A_S3_20000docs_5db_topk10_20260805_151408.json plus
the other official S1/S2/S4/S5/S6 files, compares Chroma's disk_size_mb_chroma /
disk_size_flag_chroma / effective_config.chroma (persist_directory, in_memory) across
scales for consistency (e.g. persist-mode should be uniform across scales, and disk size should
scale monotonically with num_documents if persisted, or uniformly report in_memory_no_disk if
not). Writes experiments/results/validation_report_s3_chroma_disk_<ts>.json with the specific
inconsistency found. Per explicit user direction, S3 is treated as a confirmed
requires_rerun: true regardless of what the automated check finds — the script still runs the
comparison and records its reasoning/evidence, but the report's bottom-line verdict for S3 is
fixed to true, not left to the heuristic. Never modifies the original S3 JSON or any other
official JSON.
